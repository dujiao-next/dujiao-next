# 卡网平台在线客服系统调研与建设方案

> 版本：讨论稿 v1.0 · 调研日期：2026-10-13  
> 范围：公开官方资料调研、现有仓库只读分析、产品与技术方案设计。未实施编码、部署或真实推送。  
> 说明：产品功能以对应版本、套餐和合同为准；本次未登录各产品后台做横向实测，不能将厂商宣传的 AI 解决率、到达率或用户评价当作本平台的效果保证。

## 一、结论与推荐方向

建议将系统定位为：**与订单关联的站内客服工作台，辅以 WxPusher 离线提醒**，而不是一个单独的聊天浮窗，也不是把微信推送改造成聊天系统。

第一期优先完成：

1. 用户和游客能够发起咨询，发送文字、图片，并查看历史回复。
2. 客服在统一收件箱认领、回复、转派和结束会话。
3. 会话关联已验证的订单，展示支付和交付状态，但默认不展示卡密。
4. 新咨询、未回复和离线回复通过 WxPusher 提醒，点击回站处理。
5. 消息持久化、权限隔离、附件保护、失败补偿和操作审计。

**选型建议：**

- 如果“必须在当前商城后台处理客服、深度联动订单、保持单套 Go 应用”是硬要求：选择**原生轻量客服模块**，分期建设。
- 如果“尽快具备成熟聊天体验、愿意维护独立服务”更重要：优先验证 **Chatwoot 私有部署＋平台集成层＋WxPusher**。
- 如果“不维护新服务、接受外部数据托管”更重要：优先试用 **Crisp**；极低预算可验证 **tawk.to**。
- 国内多渠道、企微、呼叫中心及企业采购需求明确后，再评估 **七陌 / Udesk**。

目前客服人数、咨询量、预算和上线时间尚不明确，因此这里给出条件式推荐，**不直接替用户锁定采购或开发路线**。无论选哪条路线，订单真实性、通知规则和 WxPusher 绑定都应由平台服务端控制。

## 二、代表性产品调研

### 2.1 产品对比

以下选取企业级、轻量 SaaS、国内服务和开源自托管四类代表，不构成市场份额排名。

| 产品 | 核心模块 | 亮点与值得借鉴的设计 | 对当前平台的适用性与边界 |
|---|---|---|---|
| Intercom | 多渠道收件箱、聊天、工单、知识中心、Fin AI、坐席辅助、主动触达 | 人工与 AI 共用客户上下文；复杂问题转人工；知识、会话和工作流统一 | 适合作为体验与 AI 协作标杆；订阅及 AI 使用费用需预算控制，卡网订单仍需定制接入 |
| Zendesk | 工单、网站消息、知识库、自动化、分析、质检、排班、集成 | 以问题解决为中心的工单生命周期；跨部门协作和管理体系完整 | 适合较大客服团队；对于小型卡网第一期可能偏重，附加能力和实施成本需报价确认 |
| Crisp | 聊天挂件、共享收件箱、客户资料、知识库、自动化、AI、报表 | 轻量一体化；客户资料与会话同屏；提供 Webhook / API，便于通知桥接 | 适合快速 SaaS 接入；官方强调套餐式定价，但坐席、AI、接口及渠道权限必须核对所选套餐 |
| Tidio | 网站聊天、Help Desk、Lyro AI、销售流程、商品卡片、分析 | 电商商品和订单上下文；行为触发咨询；人工随时接管 | 商品咨询体验值得借鉴；官方 Shopify / WooCommerce 联动不代表自动支持 Dujiao-Next，需自定义集成 |
| Chatwoot | 网站聊天、多渠道收件箱、联系人、标签、宏、自动化、帮助中心、API / Webhook | 开源自托管；三栏客服台；内部协作；数据部署位置可控 | 最值得验证的成熟自托管路线；额外运维服务和版本升级不可忽略，社区版不等于拥有全部官网功能 |
| tawk.to | 网站聊天、收件箱、工单、知识库、联系人、移动客服等 | 基础平台免费、挂件接入简单、多设备响应 | 适合低成本试运营；AI 和白标等属于附加服务，接口事件及订单嵌入能力需验证，不视为原生 WxPusher 支持 |
| 七陌 | 国内多渠道客服、机器人、知识库、工单、满意度、监控、质检、移动客服 | 网站、H5、微信、企微等统一接待；快捷回复、访客上下文、跨部门工单 | 适合国内渠道需求明确的团队；API、消息事件、部署方式和收费需售前确认 |
| Udesk | 多渠道客服、自定义工单流、知识库 / AI、坐席辅助、呼叫中心、分析、WFM | 国内及出海渠道覆盖；流程化售后；工单摘要和团队管理 | 适合更复杂的企业服务；第一期不建议照搬完整企业套件，数据位置、接口和套餐需合同确认 |

### 2.2 共通的核心模块

成熟客服系统的共通能力可以归纳为八层：

1. **接待入口**：网站 / H5 聊天挂件、商品及订单入口、工作时间、欢迎语、离线留言。
2. **会话系统**：文字、图片、历史消息、未读、发送状态、重连、会话关闭与重开。
3. **坐席工作台**：统一收件箱、认领、分配、转派、内部备注、快捷回复、检索和标签。
4. **客户上下文**：已验证身份、历史咨询、当前商品、关联订单及业务状态。
5. **售后工单**：问题类型、证据、处理人、状态、期限、升级和跨部门协作。
6. **自助与自动化**：FAQ、知识库、欢迎及离线自动回复、规则分流、后续 AI 转人工。
7. **运营管理**：响应时间、未处理积压、解决率、满意度、排班和质检。
8. **集成与治理**：API、Webhook、外部通知、权限、审计、数据导出与隐私管理。

### 2.3 最值得借鉴、但不宜全部首期实现的亮点

- **三栏工作台**：左边队列，中间会话，右边订单摘要，减少反复打开页面。
- **异步会话**：用户离开后仍可收到回复提醒，回来继续沟通，不要求双方同时在线。
- **公开回复 / 内部备注显式区分**：不同颜色和发送按钮，避免误发内部处理意见。
- **聊天与工单分工**：聊天负责沟通，工单负责跨时段处理；不能把“关闭窗口”当作售后已解决。
- **宏与快捷回复**：使用教程、发货说明和常见报错可复用，但退款承诺不得自动套用。
- **知识库优先、AI 后置**：先整理可审核的业务知识，再让 AI 推荐或生成草稿。
- **主动咨询克制使用**：支付异常时提供帮助，不以频繁弹窗打断购买。
- **不照搬输入预窥和过度访客追踪**：首期仅展示已发送内容及必要页面上下文，减少隐私风险。

## 三、当前平台现状与接入条件

仓库具备模块化单体架构，后端 Go / Gin / GORM，用户端和后台均为 Vue 3 / TypeScript；已有独立用户与管理员身份体系、Casbin RBAC，以及可选的 Redis / Asynq。

| 现有基础 | 方案影响 | 代码依据 |
|---|---|---|
| 当前客服主要为联系方式外链，Atlas 存在客服浮层 | 可将统一站内咨询入口替换 / 补充现有入口，保留外链兜底 | `frontend/user/src/templates/atlas/layout/AtlasLayout.vue` |
| 多套 storefront 模板 | 入口及会话组件应共用，覆盖 classic / vault / atlas，并适配移动端 | `frontend/user/src/templates/registry.ts` |
| 用户与管理员 JWT 分离；游客订单需要订单访问凭据 | 匿名咨询身份与订单访问权限必须分开；不能仅凭邮箱或订单号暴露订单 | `internal/app/httpserver/routes_storefront.go`、`internal/platform/http/ginutil/guest_auth.go` |
| 已有订单、支付、交付和卡密业务 | 可展示脱敏业务上下文；发货 / 退款继续使用原业务用例 | `internal/modules/order/domain/order.go`、`internal/modules/fulfillment/domain/fulfillment.go`、`internal/modules/cardsecret/domain/secret.go` |
| 通知中心已有邮件、Telegram、飞书及模板 / 日志等能力，未发现 WxPusher | WxPusher 是新增渠道，不是打开现有开关即可使用 | `internal/modules/settings/schema/messaging/notification.go`、`internal/modules/notification/application/send.go` |
| 异步通知采用 Redis / Asynq；队列禁用时不能假设提醒仍会发送 | 客服上线必须明确依赖配置，或补充持久化补偿机制 | `internal/queue/client.go`、`internal/modules/notification/infrastructure/asyncqueue/dispatch.go` |
| 已有 support 角色，其权限不仅是聊天 | 新客服应使用最小权限角色，不能直接沿用完整 support 授权 | `internal/authz/bootstrap.go` |
| 模块边界和 RBAC 有架构测试 | 原生路线需遵循 contract 通信、模块装配及路由权限覆盖 | `README.md`、`internal/architecture/` |

上述是源码能力分析，不代表线上已启用所有渠道。没有读取实际 `config.yml` 的密钥或尝试发送真实通知。

## 四、目标业务流程与功能范围

### 4.1 卡网需要重点覆盖的场景

| 场景 | 用户入口与系统行为 | 客服所需上下文 |
|---|---|---|
| 售前咨询 | 商品页咨询，自动带入商品引用 | 商品名称、规格、使用地区、交付方式、公开售后说明 |
| 付款疑问 | 支付页 / 订单页咨询，不重复提交支付 | 已验证订单的支付状态和时间；不展示支付密钥 |
| 已付款未交付 | 从订单页发起，标记交付问题 | 付款、自动 / 人工交付状态及异常摘要 |
| 卡密 / 兑换报错 | 选择订单、描述错误、上传脱敏截图 | 所购商品、交付时间、售后范围；默认不带卡密正文 |
| 补发 / 退款申请 | 从会话进入售后处理，必要时转工单 | 订单状态、申请理由、证据、原业务审核记录 |
| 游客咨询 | 可匿名问问题；关联订单前验证原订单访问凭据 | 验证通过才展示该订单有限信息 |
| 夜间留言 | 显示营业时间和回复预期，消息仍入库 | 值班通知、次日待处理队列 |

### 4.2 分期功能清单

P0 为首期必需；P1 为运行稳定后的增强；P2 为明确收益后再做。

| 模块 | P0：可运营闭环 | P1：效率与管理 | P2：扩展能力 |
|---|---|---|---|
| 用户端 | 全站入口、商品 / 订单咨询、文字 / 图片、历史记录、未读、离线留言、发送失败重试 | 会话列表、满意度、可追踪售后单、订阅客服回复提醒 | 更多渠道入口和个性化自助 |
| 客服端 | 队列、认领、回复、状态、转派、内部备注、快捷回复、订单摘要、移动端可用 | 自动分配、标签、搜索、班次、批量宏、未回复倒计时 | 技能组、负载路由、多渠道统一收件箱 |
| 售后 | 关联订单、问题分类、处理备注、跳转既有发货 / 退款页面 | 独立工单、处理期限、升级、证据及进度 | 供应商协作、结构化售后自动化 |
| 自助 | FAQ 入口、欢迎语、营业时间和离线提示 | 分类知识库、按商品推荐答案 | RAG / AI 草稿、受控 AI 自助查询 |
| 提醒 | 客服 WxPusher 绑定、新咨询 / 未回复提醒、合并、去重、发送日志与失败补偿 | 客户自愿订阅回复提醒、多渠道兜底、主管升级 | 更复杂的提醒策略和渠道优化 |
| 数据与安全 | 持久化、所有权校验、附件鉴权、限流、审计、基础积压统计 | 响应 / 解决报表、导出、保留策略、清理流程 | 高级质检与趋势分析 |

**首期不做：**电话 / 视频客服、完整 CRM、复杂排班、全渠道整合、自动退款、自动补发卡密、在微信里直接回复聊天、未经审核的 AI 自动售后决策。

### 4.3 状态与接待规则

- 会话状态：待接待 → 处理中 → 等待客户 / 等待内部处理 → 已解决；客户再次发言可以重开。
- 分配关系与状态独立：没有处理人不意味着消息丢失；客服离线不应自动结束会话。
- P0 使用值班队列＋人工认领；认领以原子操作防止两名客服同时抢占。
- 对外说明首期使用“预计回复时间”，不要承诺 24 小时人工在线。
- P1 工单单独维护新建、处理中、等待补充、已完成 / 已拒绝等状态；退款执行结果以订单系统为准。

### 4.4 界面建议

**用户端**：桌面右下角入口；移动端展开为接近全屏的会话页面，避免遮挡购买按钮。顶部显示营业状态；商品 / 订单卡片提示已关联对象；消息区和输入区常驻。订单资料只有验证后才加载。入口文案覆盖简体中文、繁体中文、英文。

**后台**：左栏“未分配 / 我的待回复 / 等待中 / 已解决”，中栏聊天及备注，右栏客户与订单摘要。发货、退款操作跳转原页面或由原服务授权执行，避免客服模块重复实现交易逻辑。

**通知设置**：全局配置应用凭据；个人页面扫码绑定 UID、查看绑定状态、发送测试、设置值班和静默时段；通知日志展示尝试次数及渠道状态，不显示 appToken。

## 五、三种建设路线

| 维度 | 原生轻量客服 | Chatwoot 私有部署＋集成层 | SaaS 挂件＋集成层 |
|---|---|---|---|
| 初期交付 | 聊天基础设施开发量最大 | 成熟会话功能可复用，平台映射仍需建设 | 基础接入最快，深度售后并非零开发 |
| 后台体验 | 可直接融入当前后台 | 初期建议独立客服台＋商城业务跳转 | 通常使用供应商后台 |
| 订单联动 | 最直接、权限统一 | 经服务端映射与脱敏接口联动 | 经接口联动，能力受套餐约束 |
| 数据掌控 | 本平台管理 | 自有部署管理，增加独立系统备份 | 需审查外部托管、导出及数据跨境条件 |
| 运维与费用 | 开发维护、实时连接、存储 | 独立运行环境、数据库 / 队列、升级及可能的许可证 | 订阅、坐席 / 用量、接口、附件及附加服务 |
| WxPusher | 平台业务事件直接触发 | Webhook 经集成层过滤后触发 | Webhook / API 经集成层触发；先验证权限和事件完整性 |
| 主要风险 | 自研可靠性和功能蔓延 | 社区版限制、双身份系统、升级兼容 | 供应商依赖、网络可达性、接口及价格变化 |

### 5.1 Chatwoot 的注意事项

官方自托管套餐页明确：社区版不包含 Captain AI、语音、定制品牌、坐席容量管理、自定义角色权限、SSO / SAML、SLA 策略等所列高级能力。**“开源可自托管”不等于所有官网能力免费可用。**

即使使用 Chatwoot，也应保留：平台身份 → 联系人映射、订单授权、客服账号 → UID 映射、消息事件幂等、通知规则和审计。不要仅把挂件嵌入页面就视为售后集成完成。

### 5.2 SaaS 验证门槛

采购前必须验证：

1. 网站和客服端在目标用户网络下是否稳定可达。
2. Webhook 是否包含客户消息、客服公开回复、内部备注标识和会话分配变更。
3. 能否服务端绑定稳定的客户标识，并验证标识不可伪造。
4. API / Webhook 所属套餐、限额、签名、重试和历史导出能力。
5. 是否允许所经营的合规数字商品业务；附件、客户信息和数据保留条款。
6. 是否能将订单上下文安全地展示给客服，而非传输完整交付正文。

## 六、WxPusher 接入专项方案

### 6.1 定位：提醒通道，不是聊天主链路

官方文档最近更新为 **2026-10-10**。相较常见旧教程，需要特别注意：

- 当前主推独立全平台客户端，支持 Android、iOS、鸿蒙和桌面端；微信 ClawBot（iLink）属于补充渠道。
- 文档列出标准推送的指令类上行回调，但 **ClawBot 渠道明确暂不支持上行消息**。不能据此承诺“所有微信提醒都能直接回复客服”。
- ClawBot 每次微信侧激活后，24 小时内最多接收 10 条，通过回复任意内容重新激活后才可继续；该限制独立于 API 发送限流。
- WxPusher 只保留约 7 天消息数据，之后不保证可靠性；平台必须自己保存聊天与提醒记录。

因此，推荐路径是：**站内收发聊天 → WxPusher 提醒 → 点击 HTTPS 链接 → 平台登录和授权 → 查看 / 回复会话。**

客服优先安装 WxPusher 客户端并实测到达；微信作为便利触达而不是唯一保障。客户订阅提醒是自愿的增强功能，不强迫安装 App 或绑定微信才能咨询。

### 6.2 采用标准推送

使用 **appToken＋UID 标准推送**，不采用 SPT 极简推送作为生产主方案。

- 标准推送可管理收件人、建立平台账号映射、使用参数二维码及回调。
- SPT 更适合个人自用提醒，不利于客服成员和客户订阅的生命周期管理。
- 客服应用与客户应用建议分离，隔离密钥、订阅文案和通知受众；具体配额归属需与官方确认，不能假设分应用能规避限流。
- **私有咨询按 UID 定向投递，不使用 Topic 群发。** Topic 面向订阅群体无差别分发，不能作为订单隐私通知的接收人授权机制。

### 6.3 客服扫码绑定流程

1. 已登录客服进入“我的提醒设置”，服务端验证权限。
2. 平台创建一次性绑定请求：关联当前管理员、应用类型、租户 / 站点、随机 nonce、过期时间；建议 5 分钟有效。
3. 服务端调用 `POST /api/fun/create/qrcode`，`extra` 放置不超过 64 位的随机关联值；不放 JWT、邮箱、管理员 ID 明文或任何卡密。
4. 客服扫码订阅，平台接收 `app_subscribe` 回调，校验 appId、绑定请求有效期和重复状态。
5. **回调仅作为扫码提示，不能直接成为最终绑定凭证。** 当前读取的 WxPusher 订阅回调章节未给出通用回调 HMAC 验签协议；系统入口跳转的签名不能套用于订阅回调。
6. 建议由服务端利用二维码 code 查询扫码 UID 复核，两次外部查询间隔不得低于 10 秒；并向候选 UID 发送一次性验证提示，让发起绑定的已登录客服完成确认。扫码抢占或 UID 不一致时废弃请求并重建二维码。
7. 验证成功后写入绑定记录、发送测试提醒；绑定变更、解绑和密钥轮换均记入审计。

查询接口返回的是**最后一次扫码者 UID**，因此二维码应短期、一次性、不公开传播。默认一个客服账号仅绑定一个 UID；需要共用通知设备时由管理员明确审批。平台解绑仅停用本站映射，是否同时取消 WxPusher 应用订阅由用户确认。

客户绑定采用同样的已登录确认与自愿授权。第一期不开放未验证匿名访客的账户级绑定；游客跨设备提醒另行设计经过验证、范围受限的访问流程。

### 6.4 事件与提醒规则

下表是建议默认值，可配置，并非 WxPusher 官方要求。

| 事件 | 接收人 | 建议触发条件 | 合并 / 终止规则 |
|---|---|---|---|
| 新会话首条有效消息 | 已分配客服；未分配时指定值班人 | 创建有效咨询且发送首条非空消息 | 不因打开挂件发提醒；短时间连发合并 |
| 用户追问 | 负责客服 | 约 60 秒后仍未读 / 未响应，或负责客服离线 | 同一会话 / 接收人约 3 分钟冷却；已读则取消普通未读提醒 |
| 首次回复超时 | 负责客服及值班主管 | 营业时间内约 5 分钟无人工回复 | 最多一个初次升级及一个后续摘要；认领本身不等于已回复 |
| 转派 / 内部提及 | 新负责人 / 被提及客服 | 有效转派或内部协作请求 | 仅通知必要人员，不向客户推送内部备注 |
| 客服公开回复 | 已自愿绑定的客户 | 约 60 秒后客户仍未读 | 合并连续回复，客户已读则取消待发送提醒 |
| 售后进度变化 | 对应客户、处理人 | 发生有意义的业务状态变化 | 不把纯内部状态变更全部通知客户 |
| 夜间咨询 | 值班人员或次日摘要 | 按营业时间和个人值班设置 | 对客户明确展示预计处理时间，不无限催促离线人员 |

在线判断采用心跳＋当前会话可见状态作参考，而不是“曾经登录”或“连接存在”。**在线仍未回复也应升级；离线并不意味着消息未持久化。**

已读提醒与未回复升级分别判断：已读可以取消普通消息提醒，但不能自动取消真正的回复超时任务。延时任务执行前重新读取会话状态、负责人、最新未读范围、绑定状态和静默设置，避免转派后提醒旧客服。

### 6.5 通知内容与跳转

推荐客服通知只包含：站点名、会话短编号、问题类别、新消息条数、等待时间和处理链接。

示例文案：

> 【Atlas 客服】有 1 个待回复咨询  
> 会话：CS-8F2A · 类型：交付问题 · 新消息：3 条  
> 请返回客服台查看。为保护隐私，提醒不展示订单详情或卡密。

客户通知采用“客服已回复你的咨询，请回站查看”，不暴露正文、订单号或联系方式。

- 首期 `contentType=1` 使用纯文本，避免用户内容中的 HTML / Markdown 被解释。
- 默认不推送原始聊天正文；如日后允许摘要，必须做脱敏、转义和截断，但不能认为正则脱敏一定能识别所有秘密。
- 不推送卡密、账户密码、验证码、支付凭据、完整邮箱、附件公开地址或 JWT。
- `url` 只指向配置过的本站 HTTPS 域名；通知标题和链接不采信用户输入的域名。
- 客服链接到移动端可用的会话页面，登录后继续跳转；后台地址必须适配可配置的 admin base。
- 会话编号只用于定位，不作为授权凭证；点击后必须重新校验账号、租户和会话权限。
- 不采用明文 UID 自动登录后台。WxPusher 的“系统对接”支持独立 HMAC 签名及时间 / nonce 校验，但**签名入口仍不应替代管理员登录与 2FA**。

### 6.6 API 与最新限制

| 项目 | 官方文档规定 / 说明 | 本方案处理 |
|---|---|---|
| 发送 | `POST https://wxpusher.zjiecode.com/api/send/message`，JSON body 使用 appToken、content、summary、contentType、uids、url 等 | 服务端 HTTPS 调用，不使用会暴露密钥和内容的 GET 发送 |
| 结果 | 顶层业务 code=1000，data 中包含逐接收人结果及 sendRecordId、messageContentId；messageId 已废弃 | 同时检查 HTTP、业务码和逐 UID 结果，记录现行字段 |
| 状态查询 | `GET /api/send/query/status?sendRecordId=...`，约 7 天缓存 | 异步抽查重要提醒，不把查询结果等同用户已读 |
| 参数二维码 | `POST /api/fun/create/qrcode`，extra 最长 64 位，validTime 单位秒 | 短期随机关联值，由服务端持有映射 |
| 扫码查询 | `GET /api/fun/scan-qrcode-uid?code=...`，轮询不得小于 10 秒 | 仅绑定页面活动期间启用服务端受控查询，离开或到期停止 |
| 内容 | 原文最多 40000 字符，UTF-8 不超过 65535 字节；转换后 HTML 也受字节上限约束 | 实际只发送短通知，不接近最大长度 |
| 摘要与链接 | summary 最长 100 字符；url 最长 1000 字符，各端展示可能进一步截断 | 摘要建议 20–40 字，链接简短 |
| 单请求接收人 | uids 最多 2000；topicIds 最多 5 | 小批次定向发送；不同接收人内容不得混成同一隐私正文 |
| 发送限流 | 默认约每 10 秒最多 20 次调用，部分应用可申请更高配额 | 全局限速、平滑发送、合并和指数退避；按实际返回及获批配额调整 |
| 客户端日用量 | 单 UID 约超过 3000 条后可能不再通知栏提醒，约超过 20000 条后可能停止列表 / 推送展示；次日恢复 | 通过冷却和摘要控制频率，不依赖极限额度运营 |
| 微信 ClawBot | 激活后 24 小时最多 10 条，需再次激活；暂不支持上行 | 微信渠道仅作补充，到达能力需要实际验证 |

接口“创建发送任务成功”仅表示被渠道受理，**不代表设备收到、微信展示或用户阅读**。站内已读状态只能由平台会话交互确认。免费服务不等于有合同级可用性保证，上线时需重新核对官方限制和服务条款。

### 6.7 可靠性、去重与失败补偿

推荐采用“持久化事件 / outbox＋异步发送”的模式：

1. 聊天消息和待处理事件在同一数据库事务落库；用户发送成功不依赖 WxPusher 响应。
2. 调度器读取 outbox，交给现有异步机制；不能把 Redis 入队成功视为唯一事件存根。
3. 发送前复核规则；幂等键至少包含事件范围、会话、接收人、渠道和合并窗口 / 消息水位。
4. 对网络失败、渠道暂时错误和限流进行指数退避＋抖动；无效 UID、配置错误或取消订阅不做无限重试。
5. 分批发送中只重试失败接收人；成功接收人的记录保持成功，避免整批重发。
6. 失败超过阈值进入待人工处理记录，并通过既有邮件 / Telegram / 飞书中的已配置渠道通知维护人员。
7. 普通提醒超过有效时间应丢弃或并入摘要；重试不能复活已经解决的会话催促。
8. 队列未启用时：原生首期可明确要求开启 Redis / worker，或设计可抢占的数据库 outbox 消费器；**禁止静默返回成功而实际上不发送。**

外部发送无法与本地数据库原子提交。请求超时但渠道实际已受理时，仍可能产生重复通知；在未发现官方客户端幂等键保证的前提下，不能承诺端到端 exactly-once。设计目标是“可补偿、可观察、尽量减少重复”，而不是虚假的零重复保证。

发送日志区分：待调度、抑制 / 合并、尝试中、渠道已受理、渠道报告失败、待重试、终止失败 / 过期。日志包含脱敏 UID、事件及会话引用、尝试次数、错误码、时间和 sendRecordId，不保存完整请求密钥。

### 6.8 外部客服平台桥接

Chatwoot 官方文档明确支持 `message_created`、`conversation_created`、`conversation_updated` 和状态变化等 Webhook。消息包含 incoming / outgoing 类型及 private 标识，但不同示例存在枚举格式差异，必须按实际部署版本规范化。

推荐桥接流程：

**Webhook → 验签 / 防重放 → 持久化事件 → 规范化消息类型 → 排除内部备注及系统消息 → 映射会话和负责人 → 应用提醒规则 → WxPusher。**

- Chatwoot 当前文档提供 `X-Chatwoot-Signature`、`X-Chatwoot-Timestamp`，按 `{timestamp}.{raw_body}` 计算 HMAC-SHA256；必须使用原始 body，并核对实际部署版本支持情况。
- 使用 delivery ID（存在时）及消息 / 事件引用去重；按 account / inbox 隔离站点。
- 客户 incoming 提醒负责客服；客服 outgoing 且非 private 的回复才可提醒客户。
- 新会话和首条消息事件避免重复提醒；分配变化重新计算收件人。
- Webhook 收到后先持久化再确认，不在回调请求中等待外部推送完成。
- 定期对账会话状态以发现事件漏投；不能假设供应商 Webhook 永不丢失。
- Crisp 官方支持 Website Hooks / Plugin Hooks，可走相同抽象流程；其具体签名、事件和套餐需进一步验证。七陌、Udesk、tawk.to 的对应能力也列为试用验证项，不虚构原生 WxPusher 插件。

## 七、原生路线技术设计边界

如选择原生路线，建议新增独立客服领域模块，以下为设计建议，不表示已创建代码或接口。

### 7.1 模块职责

- **客服模块**：会话、参与人、消息、已读水位、认领 / 转派、备注、状态及附件引用。
- **通知模块**：渠道适配、发送、重试和发送日志；扩展 WxPusher，不另造第二套渠道中心。
- **客服提醒策略**：将会话事件转换为可投递的通知命令，避免让通用通知模块反向依赖客服实体。
- **订单等业务模块**：经 contract 提供脱敏只读摘要，交易操作仍由原业务负责。
- **设置与权限**：公开入口配置和私有通知凭据分开；新增路由同步覆盖 RBAC 与角色种子。

### 7.2 数据对象

| 对象 | 必要信息 |
|---|---|
| Conversation | 站点 / 租户、用户或访客身份、关联商品 / 订单引用、状态、优先级、负责人、更新时间 |
| Message | 会话、发送人类型、公开 / 内部可见性、内容 / 附件引用、会话内序号、客户端幂等 ID、发送时间 |
| ReadCursor | 参与人已读消息水位；阅读状态不由 WxPusher 推断 |
| Attachment | 所属会话、上传者、MIME、大小、存储引用、校验状态、访问规则 |
| Assignment / Audit | 认领、转派、关闭、敏感查看及业务操作的执行人和时间 |
| NotificationBinding | 本站账号、应用、UID、验证状态、启用状态、个人偏好 |
| Outbox / Delivery | 事件、接收人、幂等键、执行时间、状态、尝试次数、渠道引用 |
| Ticket（P1） | 售后类型、订单引用、证据、处理人、处理期限、进度、处理结果 |

避免将订单实体、完整交付内容和卡密复制到聊天表或第三方联系人属性。关联引用和有限摘要已经足够支持大部分接待。

### 7.3 实时传输与一致性

- P0 可用 HTTP 发送＋鉴权 SSE 接收；WebSocket 可作为后续选项，不因“聊天”而默认增加所有双向实时能力。
- 当前代码未发现现成聊天 WebSocket / SSE 主链路，需作为新增能力规划；间接 SSE 依赖不意味着可直接启用客服功能。
- 使用会话消息序号和客户端幂等 ID 处理重复提交、顺序及断线补拉；消息入库后才返回发送成功。
- SSE 使用支持鉴权请求头的流式客户端，或设计短期、用途限定的握手机制；不把长期 JWT 放查询参数。
- 多实例需要广播机制，Redis Pub/Sub 可用于在线事件分发，但消息恢复必须依赖数据库；Asynq 是任务队列，不是实时广播。
- 原生 EventSource 自动重连不能代替历史补拉；跨页面、设备和后台恢复都应根据已读 / 已收水位补齐。
- 反向代理需验证流式连接超时、缓冲和心跳配置；实时失败可降级轮询，聊天记录不丢失。

## 八、安全与合规底线

1. **身份与订单授权分离**：游客可以咨询，但订单号、邮箱、商品截图都不能单独证明订单所有权。验证现有 Guest 凭据后授予有限关联权限；凭据不放 URL。
2. **登录 / 退出切换**：会话绑定和历史加载由服务端校验，不能仅修改前端 userId 合并访客历史；退出时清理展示状态，防止共用设备串号。
3. **最小客服权限**：会话查看、回复、转派、订单摘要、敏感交付查看、退款、发货分别授权。内部备注不能出现在客户端、客户推送或客户导出中。
4. **租户隔离**：若分销站启用，每条查询、附件及实时订阅都验证站点和所有权，通知收件人只从对应站点的可信映射产生。
5. **秘密保护**：appToken / 验证密钥仅服务端保存，按已有秘密配置模式做遮蔽；访问受限，必要时加密，支持轮换；不写前端、仓库或明文请求日志。
6. **附件保护**：首期只允许受限大小的 JPEG / PNG / WebP，例如单张最多 5 MB；检查实际内容、拒绝 SVG / 可执行文件，按需清理 EXIF，P1 增加扫描。附件通过授权访问或短期链接读取，不能直接变成永久公共 `/uploads` 链接。
7. **反滥用**：按用户 / 访客 / IP 和站点限制发言、建会话及上传频率；异常时增加验证码或封禁，不只依赖 IP。
8. **数据最小化**：上传前提示遮挡卡密；第三方只接收必要提醒。订阅说明明确第三方渠道和通知范围，支持解绑。
9. **保留与删除**：建议先以会话 180 天、提醒日志 90 天作为评审起点，非法律结论；结合交易争议、所在地要求和成本确认。附件、导出和备份需有对应生命周期策略。
10. **AI 受控**：未来只接入经过审核的知识与脱敏信息，支持人工接管；默认不得查询 / 输出卡密、自动退款或承诺超出商品售后范围的结果。

## 九、实施阶段、成本与验收

### 9.1 建议阶段

| 阶段 | 交付物 | 进入下一阶段的条件 |

- tawk.to 基础免费不代表 AI、去品牌等附加服务免费。
- WxPusher 官方当前说明为免费推送服务，但不可据此承诺永久不变、无限额度或商用 SLA。
- SaaS 需确认年度 / 月度付款、外币税费、套餐内坐席和使用额度，不仅比较首页起价。

### 9.3 首期验收清单

**业务：**

- 用户、游客、商品入口和订单入口均能创建 / 恢复会话。
- 未验证游客不能通过任意订单号看到订单、交付或卡密。
- 认领、回复、转派、等待和结束流程完整；内部备注不会发给客户。
- 已发送消息跨刷新、网络中断和后台恢复后可补齐，重复提交不会形成多条业务消息。

**WxPusher：**

- 客服扫码绑定、复核、确认、测试、解绑和轮换流程完整。
- 微信 ClawBot 激活 / 条数限制与客户端渠道差异经过真机验证；不承诺微信双向客服。
- 新咨询正确提醒；连发合并；转派不误发旧客服；客户已读后普通提醒取消；未回复超时仍能升级。
- 渠道异常不影响聊天入库；限流、无效 UID、部分成功、队列停机和补偿都有可观察结果。
- 提醒不包含卡密、密码、完整联系方式或可直接越权的链接。

**安全与性能：**

- 越权访问会话、附件、实时订阅和跨站点数据均被拒绝。
- 配置、页面和日志不泄漏 appToken；回调伪造、重放和重复投递测试通过。
- 在约定并发规模下，建议以站内消息展示 P95 ≤ 2 秒作为测试目标；外部渠道到达延迟单独统计，不计为可保证的站内指标。
- 如设计 60 秒延时提醒，应测量“延时到期到渠道受理”的耗时；不能把规则等待时间混为推送故障。
- 架构边界、RBAC 覆盖、前端多模板及多语言、反向代理和 worker 配置均通过验证。

### 9.4 运营指标

优先观测：有效新咨询量、待回复积压、首次人工响应时间 P50 / P95、超时比例、解决时间、重开率、问题类型分布、满意度，以及提醒受理 / 失败 / 合并 / 过期比例。

营业时间内响应与自然时间响应分别统计；自动欢迎语不计为首次人工回复；“发送受理”不计为客户已读或问题解决。

## 十、下一步需要确认的决策

1. 初期客服是店主一人、少量轮班人员，还是专职团队？每天大致多少有效咨询？
2. 是否必须在当前商城后台回复，还是可以使用独立客服工作台？
3. 是否接受 SaaS 存储聊天数据，或维护一个独立的 Chatwoot 服务？
4. WxPusher 首期只提醒客服，还是也让客户自愿订阅？
5. “微信提醒”是尽量支持，还是硬性要求稳定微信触达？若是后者，应额外评估正规微信 / 企微渠道，不能仅依赖 ClawBot 的有限窗口。
6. 游客售后、分销站隔离、独立工单是否是首期硬要求？
7. 可接受的首次响应目标、营业时间、保留周期、预算与上线期限是什么？

**建议默认首期组合：站内文字 / 图片咨询＋已验证订单关联＋轻量客服工作台＋仅客服侧 WxPusher＋站内持久化与邮件等可选兜底。客户提醒、完整工单和 AI 后置。**
